# بات پیام ناشناس بله (Bale)

بات پیام‌رسانِ ناشناس چندواحدی (support/رسانه/...) برای پیام‌رسان بله، با
نقش‌های **مالک** و **مدیر**، عضویت اجباری در کانال، و یک پنل مدیریت
(مینی‌اپ).

## معماری فایل‌ها

```
anon_bale_bot/
├── app.py            # composition root: فقط route ها؛ منطق کسب‌وکار اینجا نیست
├── bot.py             # منطق چت‌بات (وبهوک): پیام‌ها، کال‌بک‌ها، جریان مکالمه
├── admin_api.py        # همه‌ی APIهای پنل مدیریت (مینی‌اپ)
├── database.py           # لایه‌ی دیتابیس (PostgreSQL/psycopg3)
├── migrations.py          # نسخه‌بندی و آپدیت schema دیتابیس
├── bale_api.py             # لایه‌ی نازک ارتباط با Bot API بله
├── miniapp_auth.py          # اعتبارسنجی initData مینی‌اپ
├── config.py                 # خواندن تنظیمات از .env
├── templates/miniapp.html     # UI پنل مدیریت
├── static/style.css
├── static/app.js
├── requirements.txt
├── Dockerfile
├── docker-compose.yml
└── .env.example
```

چرا این تفکیک؟ چون فاز قبلی همه‌چیز توی یک `app.py` بود و با اضافه‌شدن
نقش‌ها/واحدها/درخواست‌ها دیگه قابل نگه‌داری نبود. الان:
- **bot.py** = هر چیزی که در چت خودِ بله اتفاق می‌افته
- **admin_api.py** = هر چیزی که در پنل مینی‌اپ اتفاق می‌افته
- **database.py** = تنها جایی که SQL می‌نویسیم
- **app.py** = فقط سیم‌کشی (wiring) این‌ها به هم

## ⚠️ آپدیت یک نصب production موجود (مهم)

این نسخه روی یک schema دیتابیس قدیمی‌تر (بدون مالک/واحد/ریپلای) اجرا
می‌شد. برای اینکه داده‌ی موجود (کاربران، گفتگوها) از دست نره، **schema
جدید رو drop-and-recreate نمی‌کنیم**؛ به‌جاش `migrations.py` یک سیستم
نسخه‌بندی ساده داره:

- هر بار اپ بالا میاد (`db.init_db()`)، لیست migrationهای اجرا شده رو
  از جدول `schema_migrations` می‌خونه و فقط migrationهای جدید رو اجرا
  می‌کنه (idempotent، امن برای اجرای مکرر).
- migration دوم (`0002_owner_units_and_reply_threading`) به‌طور خودکار:
  - یک واحد پیش‌فرض به اسم **«عمومی»** می‌سازه.
  - همه‌ی گفتگوهای قدیمی (قبل از این آپدیت) رو به همون واحد نسبت می‌ده.
  - مدیرهای فعلی (`is_admin=TRUE`) رو عضو همون واحد «عمومی» می‌کنه، تا
    گفتگوهای قبلی‌شون رو در پنل از دست ندن.
  - جدول `reply_map` رو بازسازی می‌کنه (کلید قدیمیش باگ داشت - پایین‌تر
    توضیح داده شده)؛ در نتیجه پیام‌های فوروواردشده‌ی قبل از آپدیت که هنوز
    پاسخ داده نشدن، دیگه با ریپلای مستقیم قابل پاسخ نیستن (پیام راهنما
    نشون داده می‌شه؛ خودِ گفتگو و تاریخچه‌اش دست نخورده باقی می‌مونه).
- migration سوم (`0003_admin_request_after_phone`) فقط یک ستون
  (`awaiting_admin_request`) اضافه می‌کنه؛ کاملاً بی‌خطره.

**مراحل آپدیت production:**
1. یک بکاپ از دیتابیس بگیر (`pg_dump`) — همیشه، قبل از هر آپدیتی.
2. کد جدید رو دیپلوی کن (فایل‌های جدید `bot.py`, `admin_api.py`,
   `migrations.py` رو هم اضافه کن).
3. `OWNER_PHONE` رو در `.env` تنظیم کن (پایین‌تر توضیح داده شده).
4. اپ رو ری‌استارت کن (یا `docker compose up -d --build`). migration
   به‌طور خودکار موقع بالا اومدن اجرا می‌شه.
5. مالک باید یک‌بار در چت بات دستور `/owner` رو بزنه و شماره‌ش رو تایید
   کنه (پایین‌تر توضیح داده شده) — این کار خودکار نیست.

## راه‌اندازی سریع با Docker (نصب تازه)

### ۱. آماده‌سازی `.env`
```bash
cp .env.example .env
```
مقادیر زیر رو پر کن:
- `BOT_TOKEN` — از `@botfather`
- `BASE_URL` — آدرس HTTPS عمومی سرور
- `WEBHOOK_SECRET_PATH` — یک رشته‌ی تصادفی
- `ADMIN_START_TOKEN` — یک رشته‌ی تصادفی (لینک درخواست مدیر شدن)
- `OWNER_PHONE` — شماره تلفن مالک بات (فرمت مهم نیست)

### ۲. بالا آوردن سرویس‌ها
```bash
docker compose up -d --build
```

### ۳. ثبت وبهوک
```
https://your-domain.example.com/setup-webhook
```
بعد از تست، این مسیر رو در `app.py` غیرفعال/حذف کن.

### ۴. تایید مالکیت
مالک باید در چت بات `/owner` رو بزنه و شماره‌ش رو با دکمه‌ی «تایید
مالکیت» به اشتراک بذاره. اگه شماره با `OWNER_PHONE` مطابقت داشت، نقش
مالک فعال می‌شه.

### ۵. تعریف حداقل یک واحد
مالک باید از تب «واحدها»ی پنل مدیریت، حداقل یک واحد (مثلاً «پشتیبانی»)
بسازه؛ وگرنه کاربرها نمی‌تونن انتخاب واحد کنن و پیام بفرستن. (اگه این
پروژه از یک نصب قدیمی آپدیت شده، واحد «عمومی» از قبل ساخته شده.)

## نقش‌ها

### کاربر عادی
- با `/start` وارد می‌شه، نام مستعار انتخاب می‌کنه یا «ناشناس بمونم» رو
  می‌زنه (نام پیش‌فرض: «ناشناس `<uuid>`»).
- باید یک **واحد** (دپارتمان) رو انتخاب کنه تا بتونه پیام بده.
- با `/unit` یا دکمه‌ی «🔄 تغییر واحد» هر وقت بخواد می‌تونه واحدش رو عوض
  کنه و به واحد دیگه‌ای پیام بده.
- با `/nickname` هر وقت می‌تونه نامش رو عوض کنه؛ تغییر نام به‌صورت پیام
  سیستمی داخل گفتگوش برای مدیرهای اون واحد ثبت می‌شه.

### مدیر
- با زدن لینک `https://ble.ir/YOUR_BOT?start=ADMIN_START_TOKEN`، از کاربر
  خواسته می‌شه شماره تلفنش رو با یک دکمه بفرسته؛ **درخواست مدیر شدن فقط
  بعد از دریافت همون شماره ثبت می‌شه** (نه فوری با زدن لینک) و برای مالک
  ارسال می‌شه.
- مالک از تب «درخواست‌ها»ی پنل، درخواست رو تایید/رد می‌کنه.
- بعد از تایید، مالک از تب «مدیران» مشخص می‌کنه این مدیر عضو کدوم
  واحد(ها) باشه؛ فقط گفتگوهای همون واحد(ها) رو می‌بینه.
- مدیر می‌تونه از داخل پنل (دکمه‌ی 🚪) از مدیریت **انصراف** بده؛ برای
  مدیر شدن دوباره باید دوباره لینک رو بزنه و منتظر تایید مجدد مالک بمونه.
- مالک هر وقت بخواد می‌تونه یک مدیر رو از تب «مدیران» حذف کنه.

### مالک
- با `/owner` و تایید شماره تلفن (که در `.env` با `OWNER_PHONE` مشخص
  شده) نقش مالک رو می‌گیره.
- به همه‌ی گفتگوهای همه‌ی واحدها دسترسی داره (بدون نیاز به عضویت
  دستی در واحد).
- تنها نقشی که می‌تونه: واحد بسازه/حذف کنه، درخواست مدیر شدن رو
  تایید/رد کنه، عضویت مدیرها در واحدها رو تنظیم کنه، و یک مدیر رو حذف
  کنه.

## واحدها (دپارتمان‌ها)

- هر پیام کاربر عادی به یک واحد مشخص تعلق داره؛ گفتگوی هر کاربر با هر
  واحد، جدا از گفتگوش با واحدهای دیگه ذخیره و نمایش داده می‌شه.
- اگه فقط **یک واحد** تعریف شده باشه، از کاربر واحد پرسیده نمی‌شه؛ همون
  یک واحد خودکار انتخاب می‌شه (و دکمه‌ی «تغییر واحد» هم نشون داده
  نمی‌شه، چون واحد دیگه‌ای برای انتخاب وجود نداره). به‌محض اینکه مالک
  واحد دومی بسازه، این رفتار خودکار غیرفعال می‌شه و کاربرهای جدید باید
  انتخاب کنن.
- وقتی مدیری عضو **بیش از یک واحد** باشه، در لیست گفتگوهای پنلش، کنار
  اسم هر کاربر یک برچسب واحد نشون داده می‌شه (اگه فقط عضو یک واحده،
  برچسب لازم نیست و نشون داده نمی‌شه).
- پاسخ‌های مدیر/مالک به‌صورت «📩 پاسخ از واحد `<نام واحد>`:» برای کاربر
  ارسال می‌شه (نه «پاسخ ادمین»).
- حذف یک واحد فقط وقتی امکان‌پذیره که هیچ گفتگویی به اون واحد ارجاع
  نداده باشه (برای جلوگیری از پاک شدن ناخواسته‌ی تاریخچه).

## ریپلای واقعی به یک پیام خاص

- هم در **چت خودِ بله** (مدیر روی پیام فوروواردشده در چتش ریپلای
  می‌زنه) و هم در **پنل مدیریت** (مدیر روی حباب یک پیام خاص کلیک می‌کنه
  و پاسخ می‌ده)، پاسخ به همون پیام مشخص گره می‌خوره:
  - در چت کاربر، پاسخ به‌صورت یک ریپلای واقعیِ بله روی همون پیام اصلی
    نمایش داده می‌شه (نه یک پیام مستقل).
  - در پنل مدیریت، بالای حباب پاسخ یک quote کوتاه از پیام اصلی دیده
    می‌شه.

## عضویت اجباری در کانال‌ها

قبل از پردازش **هر پیام** (کاربر عادی، مدیر یا مالک — چه در چت بات، چه
از پنل مدیریت)، عضویت در کانال‌های `config.REQUIRED_CHANNELS` بررسی
می‌شه. فعلاً فقط شامل:

- `@bonyad_shahidpalizvani`

⚠️ **نکته‌ی فنی:** برای اینکه `getChatMember` جواب درست بده، بات باید
عضو/ادمین همین کانال باشه، وگرنه به‌صورت محافظه‌کارانه فرض می‌شه کاربر
عضو نیست.

## نکات مهم / محدودیت‌های شناخته‌شده

1. نام دقیق متد گرفتن شماره تلفن مینی‌اپ (`requestContact`) رو قبل از
   انتشار نهایی با آخرین نسخه‌ی `docs.bale.ai/miniapp` مطابقت بده. راه
   جایگزین (دکمه‌ی اشتراک مخاطب داخل چت بات) همیشه در دسترسه.
2. `DEV_MODE=1` فقط برای تست محلی بدون اپ واقعی بله؛ در پروداکشن حتماً
   خاموش باشه.
3. مسیر `/setup-webhook` بدون احراز هویته؛ بعد از اولین استفاده محدود
   یا حذفش کن.
4. مقایسه‌ی شماره تلفن مالک (`OWNER_PHONE`) بر اساس ۱۰ رقم آخر شماره
   انجام می‌شه (بی‌توجه به `+98`/`0098`/`0`)، تا فرمت‌های مختلف مشکلی
   ایجاد نکنن.
5. **هرگز از `window.confirm()`/`window.prompt()` مرورگر برای تایید یک
   عملیات در `app.js` استفاده نکن.** داخل وب‌ویوی مینی‌اپ‌های شبیه بله/
   تلگرام این توابع معمولاً غیرفعالن یا بی‌صدا `false`/`null` برمی‌گردونن،
   که یعنی هر کدی که پشت `if (!confirm(...)) return;` باشه عملاً هیچ‌وقت
   اجرا نمی‌شه (این دقیقاً علت باگ‌های «حذف گفتگو/مدیر/واحد کار نمی‌کنه»
   در نسخه‌ی قبلی بود). به‌جاش از تابع `showConfirm()` در `app.js`
   استفاده کن؛ این تابع اول `WebApp.showConfirm` (اگه SDK پشتیبانی کنه)
   و در غیر این صورت یک دیالوگ HTML سفارشی (`#confirm-overlay`) نشون
   می‌ده.

## جریان دیتا (خلاصه)
```
کاربر عادی --/start--> نام مستعار --> انتخاب واحد --> پیام متنی
    پیام --> ذخیره (sender_chat_id, unit_id) --> فوروارد به مدیرهای اون واحد + همه‌ی مالک‌ها

مدیر --ریپلای روی پیام فوروارد شده یا کلیک روی حباب در پنل--> پاسخ واقعیِ ریپلای‌شده به کاربر
مدیر --در پنل--> مسدود/رفع‌مسدود کاربر، حذف گفتگو، انصراف از مدیریت

کاربر جدید --/start ADMIN_START_TOKEN--> درخواست مدیر شدن (pending) --> اطلاع به مالک
مالک --در پنل، تب «درخواست‌ها»--> تایید/رد --> در صورت تایید is_admin=TRUE
مالک --در پنل، تب «مدیران»--> عضویت مدیر در واحد(ها) رو تنظیم می‌کنه

هر کسی --/owner + اشتراک شماره--> اگه شماره == OWNER_PHONE بود => is_owner=TRUE
```
